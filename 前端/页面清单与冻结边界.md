# ClawLoops 前端页面清单与冻结边界

## 1. 为什么需要这份文档

仅有 UI 状态模型与 BFF 编排，还不足以让前端“冻结开发”。前端还需要一份明确的交付边界文档，回答三个问题：

1. MVP 首版到底要做哪些页面。
2. 每个页面最低必须实现到什么程度。
3. 哪些内容可以先不做，避免开发中途无限扩散。

本文用于冻结页面范围、最小字段、最小动作、Done Definition 与明确不做项。

---

## 2. 首版页面总表

| 一级域 | 路由 | 页面 | 必做 | 备注 |
| --- | --- | --- | --- | --- |
| 公开 | `/login` | 登录入口页 | 是 | 只展示本地密码登录方式 |
| 公开 | `/invite/:token` | invitation 接入页 | 是 | 预览 + 发起接入 |
| 已登录 | `/post-login` | 登录完成收口页 | 是 | 前端主动调 BFF |

## 3. 页面级冻结定义

## 3.1 登录入口页

最小功能：

- 展示平台品牌与说明
- 读取 `/api/v1/auth/options`
- 仅展示 `local_password`
- 按 `provider + methods[]` 渲染，首版固定文案为 `账号密码登录`
- 提供“前往登录”入口

Done Definition：

- 页面不会展示未冻结的第三方登录方式
- 已登录用户不会困在登录页

不做：

- 多身份源切换
- 忘记密码流程前端化
- 自定义密码修改页

## 3.2 invitation 接入页

最小功能：

- 展示目标邮箱
- 展示 workspace 名称
- 展示角色
- 展示有效期
- 若浏览器已有登录态，展示当前账号提示
- 若当前账号看起来与邀请邮箱不一致，展示可操作风险卡片，而不是只给提示文案
- 提供“继续接入”按钮
- 对所有 invitation 失效场景给出专门页面态

Done Definition：

- 支持有效 invitation 正常跳转 Authentik
- 支持已过期、已撤销、已消费、不存在的分支渲染
- `start` 重试安全
- 账号不一致风险会在继续接入前被明确提示
- 账号不一致风险至少提供“切换账号后继续接入”“返回登录入口”两个动作

不做：

- 前端邮箱编辑
- 前端换绑 workspace
- 手工输入 token

## 3.3 post-login 收口页

最小功能：

- 自动调用 `POST /api/v1/auth/post-login`
- 处理中展示不可交互 loading
- 按返回结果跳 `/admin`、`/app` 或无工作区页
- 对邮箱不匹配、邀请失效、同步失败提供专门错误页
- 若接入成功且落到 `/app`，必须以“接入成功确认 + 单一主 CTA”承接，而不是直接回到普通工作台视图

Done Definition：

- 刷新页面不会造成前端死循环
- 可在接口失败后手动重试
- 成功后路由落点稳定
- 普通用户登录后会落到可继续操作的页面，而不是纯中转页
- 首次接入成功后，用户能明确知道“我已加入哪个 workspace”以及“下一步只需要准备工作区”

不做：

- 前端直接消费 invitation
- 前端兜底 membership 创建

## 3.4 用户工作台

最小功能：

- 顶部展示当前用户基础信息
- runtime 卡片展示用户可理解的状态：
  - 未启动
  - 准备中
  - 可进入
  - 启动失败
- 模型列表只读展示
- 提供 `启动 / 停止 / 删除 / 进入工作区`
- 首次接入后提供“接入成功确认区”，明确显示已加入的 workspace 与下一步动作
- runtime 准备中时必须展示阶段化进度，而不是只显示一个抽象状态词

Done Definition：

- 启停删均能正确进入“进行中”态
- task 轮询结束后页面状态刷新
- `ready=false` 时不能进入工作区
- 用户不需要理解底层状态字段，也能知道下一步操作
- 用户在 runtime 准备过程中能知道当前进行到哪一步、是否可以离开、失败后先做什么

不做：

- 多 runtime 管理
- 多 workspace 切换器
- 用户自助 provider key 管理

## 3.5 workspace-entry 页

最小功能：

- 加载时请求 `/api/v1/workspace-entry`
- `ready=true` 自动跳转
- `ready=false` 显示与 `/app` 一致的阶段化准备进度，并引导回工作台
- 超时后提供手动刷新和返回工作台

Done Definition：

- 页面不依赖 `runtime/status.browserUrl` 直接跳转
- 页面可承接 post-login 成功后的下一跳
- 页面不会成为普通用户默认停留页
- 用户在此页等待时，不会退化成只看一句“环境准备中”的被动等待

不做：

- workspace 选择器
- 前端子域拼接逻辑

## 3.6 管理后台首页

最小功能：

- 加载 `GET /api/v1/admin/home`
- 展示摘要卡片：
  - `totalUsers`
  - `activeUsers`
  - `disabledUsers`
  - `pendingInvitations`
  - `expiringInvitations24h`
  - `runningRuntimes`
  - `runtimeErrors`
- 展示待办区：
  - `attention.pendingInvitations`
  - `attention.runtimeAlerts`
- 提供快捷入口：
  - 用户管理
  - 邀请管理
  - Usage 汇总

Done Definition：

- `admin` 即使没有 workspace membership，也能稳定进入首页
- 首页首屏即可发现高频任务，不需要先进入某个二级列表页
- 首页只读区与跳转区都可稳定渲染

不做：

- 自定义拖拽仪表盘
- 前端自行聚合多个后台接口做首页统计
- 首页直接承载复杂写表单

## 3.7 用户列表页

最小字段：

- `userId`
- `subjectId`
- `role`
- `status`
- `authMethod`
- `runtimeObservedState`
- `lastLoginAt`

最小动作：

- 筛选可后置
- 启用/禁用用户
- 进入用户详情

Done Definition：

- 列表可稳定展示最小字段
- 启禁用动作可用，成功后回刷

不做：

- 复杂批量操作
- 高级查询 DSL

## 3.8 用户详情页

最小功能：

- 展示用户基础信息
- 展示 runtime 详情
- 执行启用/禁用

Done Definition：

- 能区分用户状态与 runtime 状态
- 启禁用后详情回刷正确

## 3.9 invitation 列表页

最小字段：

- `invitationId`
- `targetEmail`
- `workspaceId`
- `role`
- `status`
- `expiresAt`
- `consumedAt`
- `consumedByUserId`
- `lastError`

最小动作：

- 创建
- 撤销
- 重发
- 进入详情或展开详情

Done Definition：

- 创建表单字段与后端契约一致
- 撤销/重发成功后状态回刷正确

## 3.10 模型治理页

最小功能：

- 展示全局模型列表
- 对单个模型执行更新

Done Definition：

- 支持读取和保存
- 保存后回刷数据

不做：

- 批量编排
- 模型能力可视化分析

## 3.11 provider 凭据页

最小功能：

- 展示凭据列表
- 新增凭据
- 校验凭据
- 删除凭据

Done Definition：

- 三个写操作都有显式提交态
- 删除后列表一致

## 3.12 usage 汇总页

最小功能：

- 展示全局 usage 汇总
- 支持手动刷新

Done Definition：

- 查询页稳定可用

不做：

- 前端自定义 BI 报表
- 导出中心

## 4. 全局 UI 壳层冻结

## 4.1 导航结构

首版建议壳层导航固定为：

- 用户端：
  - 工作台
  - 工作区入口
- 管理端：
  - 管理首页
  - 用户管理
  - 邀请管理
  - 模型治理
  - Provider 凭据
  - Usage 汇总

## 4.2 全局系统页

前端至少需要以下系统态页面：

- 401 未登录态
- 403 无权限态
- 用户禁用态
- invitation 无效态
- post-login 失败态
- 无工作区但可恢复态
- runtime 等待超时态
- 通用 5xx 错误态

---

## 5. 前端字段冻结清单

前端命名必须与后端一致，不允许另起别名：

- `subjectId`
- `invitationId`
- `inviteTokenHash`
- `workspaceId`
- `role`
- `desiredState`
- `observedState`
- `browserUrl`
- `internalEndpoint`
- `invitation.status`

建议前端内部 ViewModel 仅做结构归并，不改字段名。

---

## 6. 暂不冻结的内容

以下内容在三份后端文档里没有展开到足以冻结前端具体交互，因此只冻结到“页面存在 + 基础增删改查”层级：

- `/admin/models` 的高级策略布局
- `/admin/provider-credentials` 的复杂多 provider 表单编排
- `/admin/usage/summary` 的高级图表维度

处理原则：

- 首版先用表格 + 抽屉/弹窗表单完成
- 不预支复杂交互设计
- 不阻塞页面开发和路由搭建

---

## 7. 前端可以据此冻结什么

1. 页面数量与路由范围可以冻结。
2. 用户端与管理端的最小菜单可以冻结。
3. 每个页面的最小数据需求、最小动作与完成定义可以冻结。
4. 复杂但后端未展开的领域，冻结到“可开发的最小 CRUD 壳”即可。
5. 首次使用与回访使用可在同一页面承接，但必须提供不同提示文案与主 CTA。
6. 首版普通用户只会绑定 0 或 1 个 workspace，前端不需要设计 workspace 选择页。
6. 除上述暂不冻结项外，前端无需再等待后端补文档即可开始页面实现。
