# ClawLoops 前端页面清单与冻结边界（轻量认证修订）

## 1. 为什么需要这份文档

仅有 UI 状态模型与 BFF 编排，还不足以让前端“冻结开发”。前端还需要一份明确的交付边界文档，回答三个问题：

1. MVP 首版到底要做哪些页面。
2. 每个页面最低必须实现到什么程度。
3. 哪些内容可以先不做，避免开发中途无限扩散。

本文用于冻结页面范围、最小字段、最小动作、Done Definition 与明确不做项。

## 3. 页面级冻结定义

## 3.1 登录入口页

最小功能：

- 展示平台品牌与说明
- 读取 `/api/v1/auth/options`
- 仅展示 `local_password`
- 按 `provider + methods[]` 渲染，首版固定文案为 `用户名优先登录`
- 对无真实邮箱用户，登录页辅助文案必须明确“请优先使用管理员提供的用户名登录”
- 提供用户名与密码输入框
- 提供“登录”主按钮
- 命中 `mustChangePassword=true` 时必须立即跳 `/force-password-change`
- 前端不得读取或自行管理 `clawloops_session`

Done Definition：

- 页面不会展示未冻结的第三方登录方式
- 已登录用户不会困在登录页
- 登录失败会有明确错误提示

不做：

- 多身份源切换
- 忘记密码流程前端化
- 自定义密码修改页

## 3.2 首登强制改密页

最小功能：

- 只允许已登录且 `mustChangePassword=true` 的用户访问
- 明确说明当前正在使用默认初始密码，需要先修改后才能继续
- 提供当前密码、新密码、确认新密码输入框
- 提供“更新密码并继续”主按钮
- 成功后直接进入 `/admin`

Done Definition：

- 种子管理员第一次使用默认密码 `admin` 登录后，不会进入 `/admin` 壳层
- 改密成功前无法访问其他业务页
- 改密失败会有明确表单级错误提示

不做：

- 从导航主动访问的通用改密入口
- 普通用户自助改密
- 找回密码

## 3.3 账号禁用说明页

最小功能：

- 展示“账号已禁用，请联系管理员”说明
- 提供返回登录页或退出当前会话入口
- 不依赖业务接口继续加载数据

Done Definition：

- 当 `/auth/access.reason=USER_DISABLED` 时有稳定承接页
- disabled 用户不会继续停留在 `/app` 或 `/admin` 主内容区

不做：

- 自助申诉流程
- 在线解封流程

## 3.4 无权限页

最小功能：

- 展示“无权限访问当前页面”说明
- 提供返回首页或返回上一页入口
- 统一承接非 admin 访问 `/admin/*` 的场景

Done Definition：

- 非 admin 误入后台时不会看到半截后台内容
- 权限不足场景不与账号禁用页混用

不做：

- 细粒度权限申请流

## 3.5 invitation 接入页

最小功能：

- 展示推荐登录账号；必要时再展示目标邮箱槽位
- 展示 workspace 名称
- 展示角色
- 展示有效期
- 提供初始密码与确认密码输入框
- 提供“设置初始密码并继续”按钮
- 对所有 invitation 失效场景给出专门页面态
- 若用户属于无真实邮箱场景，不要求其理解或记忆代理邮箱
- 若 `accept` 返回 `replayed=true`，仍按成功接入处理

Done Definition：

- 支持有效 invitation 正常在站内完成接入
- 支持已过期、已撤销、已消费、不存在的分支渲染
- `accept` 重试安全
- 用户名不一致风险会在提交后给出明确提示
- 无真实邮箱用户能仅凭用户名提示完成接入
- 幂等重放成功不会把用户误导为失败

不做：

- 前端邮箱编辑
- 前端换绑 workspace
- 手工输入 token

同路由独立页面态：

- invitation 不存在页
- invitation 已过期页
- invitation 已撤销页
- invitation 已消费页

## 3.6 用户工作台

最小功能：

- 顶部展示当前用户基础信息
- runtime 卡片展示用户可理解的状态：
  - 未启动
  - 准备中
  - 可进入
  - 启动失败
- 首次接入成功后，首屏给出“已成功加入 workspace”的确认信息
- 提供单一主 CTA 引导“开始准备工作区”或“继续准备工作区”
- 展示模型只读列表

Done Definition：

- 首次接入成功后用户不会迷失在中转页
- 普通回访用户与首次接入用户都能在 `/app` 完成承接
- runtime 状态与动作语义不混用

不做：

- workspace 选择页
- 用户自助 provider key 配置页
- 首版复杂 onboarding 向导

## 3.7 工作区入口页

最小功能：

- 根据 `/workspace-entry` 判断是否可跳转
- 仅在 `ready=true` 时整页跳转 `browserUrl`
- 在等待就绪时展示稳定 loading 与重试
- 跳转时不向 `browserUrl` 附加任何鉴权参数

Done Definition：

- 不直接依赖 `runtime/status` 作为最终跳转依据
- 用户能明确知道当前是在“等待可进入”还是“已经可进入”
- workspace 可进入性完全依赖平台 session，不依赖前端自行拼 token

不做：

- 复杂工作区选择
- 前端自行拼接 `browserUrl`

## 3.8 管理后台

最小功能：

- `/admin` 是真实首页而不是跳板页
- 用户治理、邀请治理、模型治理、provider 凭据、usage 汇总都可直达
- 后台壳层稳定
- 当 `mustChangePassword=true` 时，后台壳层不可进入

Done Definition：

- 非首登强制改密场景下，admin 登录后默认进入 `/admin`
- 非 admin 用户进入后台会被稳定拦截
- 首登强制改密完成后才允许进入后台首页

## 4. 本次删掉的页面与流程

以下内容从旧方案中删除，不再作为首版页面或流程存在：

- `/post-login`
- 外部登录跳转页
- enrollment flow 中转
- 邀请接入后的二次收口页

这些职责统一改由：

- `/login`
- `/disabled`
- `/403`
- `/force-password-change`
- `/invite/:token`
- `/app`

以上页面共同承接。

---

## 5. 首版明确不做

- 通用改密页面
- 找回密码页面
- 邮箱验证页面
- 第三方登录入口
- 多因素认证页面
- 前端自管 session cookie 生命周期
- 前端直连 `/internal/auth/workspace-access`

---

## 6. 最终边界结论

前端只需要围绕五件事设计：

1. 登录
2. 异常访问收口
3. 首登强制改密
4. invitation 接入
5. runtime 工作区进入

其余认证扩展能力全部留到后续版本。
